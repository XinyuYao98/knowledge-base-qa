## 5.1 术语与组件说明（写给"看不懂技术栈表"的人）

技术栈表里混着几个名字，功能容易混淆。这里逐个说清它们**解决什么问题**、**不解决什么问题**。

### 5.1.1 psycopg —— Python 连 PostgreSQL 的驱动

**它是什么**：Python 程序与 PostgreSQL 数据库之间的"翻译官"。

```
Python 代码  ──psycopg──>  PostgreSQL
sql.execute("SELECT ...")    返回结果集
```

**为什么需要它**：Python 本身不会说 PostgreSQL 的网络协议。psycopg 实现了这个协议，把 Python 的调用翻译成 SQL 发给数据库，再把结果翻译回 Python 对象。

**它不是什么**：它不做 ORM（不把你的类映射成表），那是 SQLAlchemy 的活。实际上本项目是 `SQLAlchemy(ORM) → psycopg(驱动) → PG` 这样的三层。

**为什么选它而不是 `psycopg2`**：`psycopg` 是 psycopg3，原生支持 async/await，且支持连接池的异步版本。`psycopg2` 是上一代，只有同步版本。本项目是 FastAPI 全异步，用 `psycopg2` 会把事件循环堵死。

**许可证为什么是 LGPL-3.0**：LGPL 要求"修改了它的源码就要开源"，但**只是从外部 import 使用、不修改源码，不触发这条义务**（这叫"动态链接豁免"）。你 MIT 项目依赖它完全合法，只要不把它的源码改一遍再打包进去。

> 对表格中"动态链接，不传染"这句话的准确理解：**LGPL 传染的是"对库本身的修改"，不是"使用这个库的程序"。**

### 5.1.2 本地 GGUF 服务 —— 让程序能调用你显卡上的模型

**先看没有它会怎样**：

你想用 Qwen3-Embedding-4B 把文本变成向量。但这个模型是一个 `.gguf` 文件（2.5GB 的二进制权重），它自己不会响应 HTTP 请求，也不认识 JSON。

你的后端代码需要一个东西：**发一个 HTTP 请求过去，它把文本转成向量回给我**。

这个"东西"就是本地 GGUF 服务。它做三件事：

| 步骤 | 说明 |
|---|---|
| 1. 把 GGUF 权重加载进显存 | 一次性动作，启动时做 |
| 2. 监听一个 HTTP 端口 | 通常是 `http://127.0.0.1:1234/v1` |
| 3. 把请求里的文本喂给模型，返回向量 | 这就是 `/v1/embeddings` 这个接口 |

```
你的后端                      GGUF 服务                   GPU
─────────                    ──────────                 ─────
POST /v1/embeddings   →      加载好的 4B 模型      →      计算
{"input": ["差旅标准"]}      （权重常驻显存）               ↓
                     ←      {"embedding": [0.023, ...]}  ←
```

**为什么叫"OpenAI 兼容"**：因为 OpenAI 把 `/v1/embeddings` 这个接口的请求格式、响应格式定成了事实标准。LM Studio、Ollama、vLLM、TEI、Xinference 全都实现了一模一样的格式。

**这对你的意义（也是当初选这条路的核心理由）**：

```python
# 只改一个环境变量，就能把底层从 LM Studio 换成 vLLM 换成 Ollama
EMBED_BASE_URL=http://127.0.0.1:1234/v1   # LM Studio
EMBED_BASE_URL=http://127.0.0.1:8080/v1   # vLLM
EMBED_BASE_URL=http://127.0.0.1:11434/v1  # Ollama
```

代码一行不改。这就是为什么架构里说"只认 `EMBED_BASE_URL`，实现无关"。

**两种可选实现**（你两个都要会）：

| 实现 | 用途 | 优点 | 缺点 |
|---|---|---|---|
| **LM Studio**（你现在用的） | 本地开发 | 图形界面、点几下就能加载模型、能看到显存占用 | 是个桌面软件，别人部署时得先装它 |
| **llama-cpp-python**（项目分发用） | 给别人用 | 纯 Python 库，`pip install` 就行，可打包进 Docker | 需要自己写启动脚本（约 30 行） |

项目会提供 `scripts/start-embedding.py`，用 llama-cpp-python 加载同一个 `.gguf` 文件，暴露同样的 `/v1/embeddings`。这样别人 clone 你的仓库后，**不需要安装 LM Studio 也能跑**。

**它不是什么**：
- 它不是"AI 大脑"——它只做"文本 → 向量"这一件事，**不会回答问题**
- 它不是 RAG 的一部分——RAG 是流程，它只是流程中被调用的一个外部服务
- 它不加载问答模型——问答模型是**用户自己配置的云端 API**（D8），两者完全不同的东西

**一张图说清三个模型分别在哪**：

```
用户提问
   ↓
【你的系统】
   ├─ 检索阶段 → 调【本地 GGUF 服务】把问题转成向量，去 Chroma 找相似文档
   │            （这里是 Qwen3-Embedding-4B，跑在你的 4060 上）
   │
   └─ 生成阶段 → 把找出的文档 + 问题，发给【用户的云端 LLM】
                （这里是 DeepSeek / 通义 / GPT，跑在别人机房，你的卡不参与）
```

### 5.1.3 `OpenAIEmbeddings` —— LangChain 里的一个"适配器类"

这是你第二个问题的直接答案。

**它是什么**：LangChain 提供的一个 Python 类。它的作用是**把你的"调用向量服务"这件事，包装成 LangChain 生态统一的接口**。

**为什么需要这层包装**：如果没有它，你要自己写 httpx 请求：

```python
# 不用 LangChain 的写法 —— 能跑，但要自己处理重试/超时/批量/错误
resp = httpx.post(
    f"{base_url}/embeddings",
    json={"model": model, "input": texts, "dimensions": 2560},
    headers={"Authorization": f"Bearer {key}"},
    timeout=60,
)
vectors = [d["embedding"] for d in resp.json()["data"]]
```

```python
# 用 OpenAIEmbeddings —— 一行
emb = OpenAIEmbeddings(base_url=..., api_key=..., model=..., dimensions=2560)
vectors = emb.embed_documents(texts)    # 批量
vector = emb.embed_query(question)      # 单条（自动带查询指令前缀的变体）
```

**它做的事（真实的，不是包装好看而已）**：

| 能力 | 说明 |
|---|---|
| 批量与分片 | 自动按批次切分长列表，避免单次请求过大 |
| 重试 | 内置对 429 / 5xx 的退避重试 |
| `embed_query` vs `embed_documents` | 区分查询侧与文档侧（有些模型需要不同的前缀） |
| 统一接口 | 换成 OpenAI 官方、Azure、本地 vLLM、本地 GGUF，**代码不变，只改构造参数** |

**它不是什么**：

- ❌ 它**不是**"必须用 OpenAI 的服务"。名字里带 OpenAI，是因为它实现了 OpenAI 的接口协议。你传 `base_url=http://127.0.0.1:1234/v1`，它连的就是你本地的 LM Studio，一个 token 都不会发给 OpenAI。
- ❌ 它**不是**向量数据库。它只负责"文本 → 向量"，不负责存储和检索。
- ❌ 它**不包含模型**。它是个 HTTP 客户端，模型在服务端（你的 GGUF 服务里）。

**为什么表格里写"（连本地 GGUF 服务）"**：

因为这个名字最容易让人误以为"要用 OpenAI 的付费 API"。我们实际用法是：

```python
emb = OpenAIEmbeddings(
    base_url="http://127.0.0.1:1234/v1",   # ← 指向本地 LM Studio
    api_key="not-needed",                   # 本地服务不校验，占位即可
    model="qwen3-embedding-4b-q4km",
    dimensions=2560,
)
```

**一句话**：`OpenAIEmbeddings` = 一个会说 OpenAI 方言的 HTTP 客户端，你让它连谁它就连谁。在这里它连的是你显卡上的模型。

### D4 · 索引原子性 【已定】

**问题**：索引写到一半失败，Chroma 留下半成品向量 → 检索能命中"未完成"的文档。

**方案**：`documents.status` 是唯一检索入口。
- 开始时 `status='embedding'`，全部写入成功才置 `'ready'`
- 检索时 PG 只返回 `status='ready'` 的 doc_id 并用于过滤 Chroma

半成品天然不可见，**无需"临时 collection + 原子切换"**那套复杂机制。

### D5 · LangChain 只用 L1 组件层 【已定】

| 用 | 不用 |
|---|---|
| `OpenAIEmbeddings`（连本地 GGUF 服务） | `create_retrieval_chain` |
| `ChatOpenAI`（连用户模型） | `ConversationalRetrievalChain` |
| `Chroma`（vectorstore 封装） | LCEL 管道编排 |

**理由**：本项目最有价值的代码是"RRF 融合 + 引用校验 + 一次修复 + 降级"，LangChain 无现成实现；用框架编排会把它们拆散到多个 hook，降低可读性与可讲述性。

#### D6-b · 模型服务的启动时序（v3.2 补充）

**结论：每次提问都必须有 embedding 服务在跑；但大部分开发工作不需要它。**

| 场景 | 需要 LM Studio | 原因 |
|---|---|---|
| 上传文档后的索引过程 | ✅ 必须 | 切块后要向量化 |
| **每一次提问** | ✅ 必须 | 问题要先转成向量才能检索（**这是最容易被忽略的一点**） |
| 写代码 / 跑单元测试 | ❌ 不需要 | 解析、切块、引用校验都是纯函数；embedder 在测试中注入假实现 |
| 启动 API / 前端 / 看质量看板 | ❌ 不需要 | 启动过程不调模型 |
| 重跑 P8 之后的评测集 | ✅ 需要 | 评测要真实作答 |

**四条工程约束（由这个时序推导出来）**：

1. **Embedder 必须是接口**，不能是硬编码的 HTTP 调用 —— 否则单测全部依赖外部服务
   ```python
   class Embedder(Protocol):
       async def embed_documents(self, texts: list[str]) -> list[list[float]]: ...
       async def embed_query(self, question: str) -> list[float]: ...

   class FakeEmbedder:          # 测试用：返回确定性向量
       async def embed_documents(self, texts): return [[0.1] * 2560 for _ in texts]
       async def embed_query(self, q):         return [0.1] * 2560
   ```

2. **索引任务在模型不可达时转 `waiting_model`，不标失败** —— 否则模型晚起 5 分钟，用户重传的文件全部变成 `failed`

3. **问答在模型不可达时立即报错并给出可操作提示**（「向量服务未启动，请先打开 LM Studio」），不要静默降级成空结果

4. **README 必须写明启动顺序**：
   ```
   1. 打开 LM Studio，加载模型，启动本地服务（端口 1234）
   2. docker compose up -d
   3. make dev
   ```
   顺序颠倒会导致索引任务卡在 `waiting_model`、问答全部报错 —— 这是新手最常踩的坑。

### D7 · 模型可替换 + 换模型检测 【已定】

- 配置项 `EMBED_BASE_URL` / `EMBED_MODEL` / `EMBED_DIM`
- `documents.embed_model` 记录生成向量的模型标识
- 启动校验：当前配置与库中记录不一致 → 拒绝服务并提示 `make reindex`
- 理由：换模型必换向量空间，不校验会产生"检索结果全是噪声但系统不报错"的隐性故障

### D8-b · 命名规则与删除策略（v3.2 新增）【已定】

**知识库命名**：

| 规则 | 实现 |
|---|---|
| 空白处理 | 入库前 `strip()`，首尾空格不计入名称 |
| 大小写 | **敏感**（`Financial` 与 `financial` 视为两个库） |
| 长度 | 1-100 字符（strip 后计） |
| 唯一性 | `UNIQUE(user_id, name)` 在 strip 后的值上生效 |
| 冲突提示 | 「已有同名知识库，请换一个名称」 |

> 为什么大小写敏感：中文用户不会用大小写区分名称，但英文用户会。
> 折叠大小写会造成"我明明建了 Financial，它说重名"的困惑，成本大于收益。

**删除策略：物理删除 + 前端强确认**

```
用户点"删除知识库"
  ↓
弹窗要求手动输入知识库名称
  ↓
输入一致才启用"确认删除"按钮（危险红）
  ↓
后端 DELETE → 级联删除 documents / chunks / Chroma collection / BM25 索引
```

**明确不做软删除/回收站**，理由：

1. 软删除会给所有查询多加一个 `deleted_at IS NULL` 条件，**漏写一处就是已删数据泄露**——这正是选 Chroma 后最该避免的那类 bug
2. 强确认交互能挡住 90% 的误操作，成本几乎为零
3. 这是演示项目，数据可重建

**必须在 README 声明的风险**：删除不可恢复，且**没有备份机制**（见 §15）。

### D9 · 索引任务队列 【已定】

DB 任务表 + `FOR UPDATE SKIP LOCKED`，不引入 Celery/Kafka。
- 最多 3 次尝试，退避 1/5/15 分钟 ±25% 抖动
- 单任务墙钟上限 30 分钟
- worker 启动回收停滞 30 分钟以上的 `running`

### D10 · 上传 【已定】

- 5MB 分片，支持乱序与续传
- 先预扣配额：`UPDATE ... WHERE used_bytes + size <= quota_bytes`，原子不超卖
- 秒传：同库 sha256 命中直接复用
- 合并需读入内存 → 单文件 200MB，峰值约 200MB × 并发 2 = 400MB，4GB 机器可承受

### D11 · 引用校验与修复 【已定】

三道：
1. **无召回 → 不调 LLM**，"未找到"
2. **强制逐句 `[n]` 引用**（prompt 规则 A-H）
3. **机械校验**：编号越界 + 数字/编号溯源 → 失败一次修复 → 仍失败则剔除越界编号并打标

**技术边界（诚实写入 README）**：只能查"编号对不对""数字在不在"，**查不出"引用了正确编号但内容张冠李戴"**。语义级忠实度校验需额外 NLI 调用，一期不做。

### D12 · 登录（v3.1 调整）【已定】

| 项 | 规则 |
|---|---|
| 账号标识 | **用户名**：3-20 字符，`[a-zA-Z0-9_]`，唯一 |
| 密码长度 | **6-12 位** |
| 密码字符 | **仅数字 + 英文字母大小写**，且**必须至少包含一个字母和一个数字** |
| 哈希 | argon2id（`time_cost=3, memory_cost=64MB, parallelism=2`） |
| 令牌 | access 15min（内存）+ refresh 7d（httpOnly cookie） |
| **登录限流** | **每用户名 5 次/分钟 + 每 IP 5 次/分钟**，双维度独立计数 |
| 失败提示 | 统一返回"用户名或密码错误"（防账号枚举，不区分"用户不存在"与"密码错"） |

**必须写进 README 的安全声明**：6 位纯数字密码只有 100 万种组合，现代显卡离线爆破是秒级的。本项目的密码策略是"演示项目从简"，**迁移到生产环境必须改为 ≥12 位 + 增加邮箱验证 + 增加登录失败锁定**。限流不是锦上添花，是这套弱密码策略下唯一能挡住在线爆破的手段。

**明确缺失**：无邮箱验证、无找回密码、无二次验证。

### D13 · 多轮对话与查询改写（v3.1 新增）【已定】

**问题**：用户问"那它的上限呢"，检索系统只看到这句孤立的话，向量召回会失败。

**方案：按需查询改写（Conditional Query Rewrite）**

```
检测指代词（它/这个/那个/上述/前者/后者/该/此/这几个/刚才说的…）
  ├── 命中 → 调用户配置的 LLM，把问题改写成完整问句 → 用改写后的问题做三路召回
  └── 未命中 → 直接用原问题召回，零额外调用
```

| 项 | 决策 |
|---|---|
| 改写模型 | **用户配置的 LLM**（不额外加载本地模型，不挤占 8GB 显存） |
| 触发条件 | 正则命中指代词 **且** 会话轮次 > 1（首轮无历史可指代） |
| 超时 | 5s，超时则降级用原问题（不阻塞主线） |
| 失败处理 | 改写失败 → 用原问题 + 标 `degraded=no_rewrite` |
| 额外延迟 | 命中时 +300-800ms；未命中时 0 |

**为什么不做无条件改写**：每轮都改写会额外消耗用户 token 且增加延迟，而"每轮都有指代词"是不成立的假设。用一行正则筛掉 70% 的调用，是"感知不到延迟"与"多轮体验好"的平衡点。

**改写 Prompt（独立版本管理，`rewrite_v1.0.0.md`）**：
```
把用户的最新问题改写成一个不依赖上下文的完整问句。
规则：
1. 只补全指代与省略，不改变问题意图
2. 不引入对话中没有的信息
3. 输出改写后的问题本身，不要加任何解释
4. 若最新问题本身已完整，原样输出

对话历史：
{history}

最新问题：{question}
```

### D1-b · RRF 融合的原理（写进 README 的科普段）

**问题**：向量给余弦相似度（集中在 0.6-0.9，分差极小），BM25 给无上界分数（可达 30+，分差巨大）。直接相加，BM25 会完全压过向量；按比例缩放则要针对每个库重新统计分布，不可维护。

**RRF 的做法**：不看分数，只看名次。

```
score(d) = Σ_{通路 i} 1 / (k + rank_i(d))
```

示例（k=60，两路各召回 3 条）：

| 文档 | 向量排名 | BM25 排名 | 计算 | 总分 |
|---|---|---|---|---|
| A | 1 | 未召回 | 1/61 | 0.01639 |
| B | 2 | 1 | 1/62 + 1/61 | **0.03252** |
| C | 4 | 2 | 1/64 + 1/62 | 0.03175 |
| D | 3 | 未召回 | 1/63 | 0.01587 |

结果：B > C > A > D。B 在向量排第 2、BM25 排第 1，两路都认可 → 胜出；A 在向量排第 1，但 BM25 完全没召回，只有一路支持 → 输给 B 和 C。

**k=60 的作用**：控制"名次差异的权重"。

| k 值 | rank=1 | rank=10 | 比值 | 含义 |
|---|---|---|---|---|
| 0 | 1.0 | 0.1 | 10× | 极度信任名次 |
| **60** | 0.0164 | 0.0143 | **1.15×** | 第 1 与第 10 差距仅 15%，强调"多路共识" |
| 1000 | 0.001 | 0.00099 | 1.01× | 几乎抹平名次 |

60 是 RRF 原论文（Cormack et al., 2009, SIGIR）在 TREC 数据集上的实证最优值，不是理论推导。工业界 90% 场景直接沿用。调参方向：某路明显更可靠时调小 k（20-40），融合结果太"平"时调小，太"尖"时调大（80-100）。

**为什么用 RRF 而不是加权求和**：余弦相似度 ∈ [-1,1]，BM25 分数无上界，量纲不同；加权需归一化调参且随库变化，RRF 只用排名，免疫量纲，且单路失败时另一路仍能排序。

**为什么 Rerank 是必需而非可选**：RRF 只做排名融合，不理解"问题与文档的语义匹配强度"；cross-encoder 逐对打分能把"字面重叠但语义无关"的候选压下去。中文同义词密集时差异明显。
