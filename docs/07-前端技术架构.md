## 一、需要立即修复的后端阻塞项（F1 必做）

### 1.1 CORS 未放行开发端口

**实测**：

```python
# app/core/config.py:34
CORS_ORIGINS: str = "http://localhost:3000"
```

Vite 默认端口是 **5173**。不同过这一条，前端所有请求会被浏览器拦在 CORS 预检阶段。

**方案**：`.env` 中改为

```
CORS_ORIGINS=http://localhost:5173,http://127.0.0.1:5173
```

这是**配置改动**，不改代码。

### 1.2 流式穿透验证

`/query/stream` 是 `POST` + `Authorization` 头，经 Vite 代理转发。F1 末尾用一个真实的 mock SSE 端点验证：

- 浏览器 Network 面板能看到 `text/event-stream`
- 事件逐条到达，不是最后一次性收到

**为什么 F1 就验**：流式一旦被缓冲，F4 的所有问答工作都是白做。

## 三、请求层设计（`api/http.ts`）

### 3.1 职责

| 职责 | 做法 |
|---|---|
| 注入 token | 从 `sessionStorage` 读，拼 `Authorization: Bearer {token}` |
| 统一 baseURL | `VITE_API_BASE`（开发为 `/api`，走 Vite 代理） |
| 解析错误体 | 后端是 `{code, message, trace_id, detail?}`，直接取 `message` 展示 |
| 401 处理 | 清 token → 跳 `/login?redirect=当前路径` |
| 超时 | 默认 30s；上传单独 120s |
| trace_id | 错误时打 `console.error`，便于对日志 |

### 3.2 错误类型

```ts
// 后端 AppError.to_payload() 的镜像
interface ApiErrorBody {
  code: string
  message: string
  trace_id?: string
  detail?: Record<string, unknown>
}

class ApiError extends Error {
  constructor(public status: number, public body: ApiErrorBody) {
    super(body.message)
  }
}
```

**为什么要把 `code` 单独留着**：后端用 `code` 做前端分支（如 `kb_not_ready`、`quota_exceeded`），`message` 直接给用户看。混在一起会逼前端解析中文文案。

### 3.3 不做的事

- **不做请求重试**：后端已按 `retryable` 分类，但自动重试会让「上传」这类非幂等请求出问题。只在**问答**处做一次用户手动「重试」按钮。
- **不做全局 loading 遮罩**：演示场景下，全屏遮罩会让画面卡顿感更强。改为组件内骨架屏。

## 四、SSE 解析器设计（`api/sse.ts`）

### 4.1 为什么手写

后端实际协议（`_sse()` 实现）：

```
event: meta
data: {"citations":[...], "question":"...", "rewritten":false, "retrieve_ms":812.3}

event: delta
data: {"text":"一线"}

event: done
data: {"answer":"...", "citation_ok":true, "caveat":"", "duration_ms":...}

event: end
data: {}
```

`EventSource` 不支持自定义头 → token 只能塞 URL → **凭证进 access log**。所以用 `fetch` + `ReadableStream`。

### 4.2 必须处理的三个边界

| 边界 | 说明 |
|---|---|
| **分帧不完整** | 一个 TCP chunk 可能切在 `data: {"te` 中间，必须按 `\n\n` 缓冲，不能逐 chunk 解析 |
| **多字节字符截断** | 中文 UTF-8 是 3 字节，跨 chunk 时 `TextDecoder` 必须用 `{stream: true}` |
| **`done` 与 `end` 的区分** | `done` 带最终结果（citations、citation_ok、caveat），`end` 只是关闭标记 |

### 4.3 接口形态

```ts
type StreamEvent =
  | { event: 'meta'; data: { citations: Citation[]; question: string; rewritten: boolean; retrieve_ms: number } }
  | { event: 'delta'; data: { text: string } }
  | { event: 'done'; data: DonePayload }
  | { event: 'error'; data: { message: string } }

async function* streamQuery(
  kbId: string,
  question: string,
  history: ChatTurn[],
  signal?: AbortSignal,
): AsyncGenerator<StreamEvent>
```

用 `AsyncGenerator` 而不是回调：Vue 里 `for await` 直接更新响应式变量，比回调更直观。

### 4.4 中断

用户点「停止」→ `AbortController.abort()` → 前端保留已收到的部分文本，标注「已中断」。

**必须做**：流式没有中断手段，用户一旦提问就只能等（实测 p50 8-11s，遇到慢查询会更久）。

## 五、状态管理

极简。**只用 Pinia 存两样东西**：

```ts
// stores/auth.ts
token: string         // 与 sessionStorage 同步
user: { id, username, created_at } | null   // 对应后端 UserResponse

// stores/kb.ts
currentKb: Kb | null  // 从路由参数 hydrate
```

**不放进 store 的**：页面数据（库列表、文档列表、消息记录）全部用 `ref` 放在组件里。

理由：这个应用是「单用户、单页面操作」形态，没有跨页面共享列表数据的需求。放进 store 只会增加「什么时候该清空」的心智负担。

## 六、路由与守卫

```
/login                   登录/注册（未登录可访问）
/                        → 重定向到 /kbs
/kbs                     知识库列表
/kbs/:id                 知识库详情（文档列表）
/kbs/:id/chat            问答
```

守卫规则：

| 条件 | 动作 |
|---|---|
| 无 token 访问非 `/login` | 跳 `/login?redirect={当前路径}` |
| 有 token 访问 `/login` | 跳 `/kbs` |
| 登录成功 | 跳 `redirect` 或 `/kbs` |

**注意**：守卫只做「有没有 token」的粗判，**不做 token 有效性校验**（那要发请求）。token 过期的表现是第一个接口返回 401，由请求层拦截器跳登录。

## 七、页面与交互

### 7.1 登录/注册（`LoginView`）

- 单页 Tab 切换登录 / 注册
- **用户名 + 密码**（不是邮箱——后端 `RegisterRequest` 与 `LoginRequest` 的字段都是 `username`）
- 前端校验（必须与后端约束一致，见下表）
- 错误直接展示后端 `message`（如「用户名已存在」「用户名或密码错误」）
- 成功后写 `sessionStorage` + store

#### 字段约束对照（已核对代码，别凭印象写）

| 字段 | 注册 | 登录 | 来源 |
|---|---|---|---|
| `username` | 3–32（Pydantic） | 1–64（Pydantic） | `auth.py:33` / `auth.py:38` |
| `password` | 8–128 | 1–128 | `auth.py:34` / `auth.py:39` |

**前端校验的取值必须用后端注册的约束**：用户名 3–32、密码 ≥ 8。
登录框不要做长度下限（后端只要求 ≥1，用户输错了让后端返回统一错误）。

#### ⚠️ 已发现的约束冲突（F2 必须处理）

数据库对用户名的约束比 Pydantic 更严：

```sql
-- migrations/001_init.sql
CONSTRAINT ck_users_username_len CHECK (char_length(username) BETWEEN 3 AND 20)
```

而 `RegisterRequest` 允许 **3–32**。实测推演：

```
用户名 21 个字符 → Pydantic 通过 → 写库触发 check 约束失败
```

**表现是对用户报 500，而不是「用户名过长」这种可读提示。**

两种修法：

| 方案 | 做法 | 影响 |
|---|---|---|
| **A（推荐）** | 把 `RegisterRequest.max_length` 改成 20 | 改一行，前后端约束一致 |
| B | 放宽 DB 约束到 32 | 要写迁移，且需要确认没有下游依赖 20 的上限 |

➡️ **推荐 A**。改一行代码就能消除 500，而且 DB 是最终事实，让 API 层对齐它比反过来安全。

**若选 A**，则前端校验 `username` 长度为 **3–20**。

### 7.2 知识库列表（`KbListView`）

- 卡片网格（`Card`），每张卡：库名、文档数、创建时间、进入按钮
- 右上角「新建知识库」→ `Dialog`（名称 + 描述）
- **空态**：引导文案 + 大按钮（对外演示时这是第一印象）
- 删除库：二次确认 `AlertDialog`，提示「将删除全部文档与索引，不可恢复」

### 7.3 知识库详情（`KbDetailView`）

- 顶部：库名 + 文档数 + 「去问答」按钮
- 文档表格（`Table`）：文件名、类型、大小、页数、状态、上传时间、操作
- 状态徽标：
  - `pending` / `parsing` / `indexing` → 蓝色 `Badge`「处理中」+ `Progress`
  - `ready` → 绿色 `Badge`「可用」
  - `failed` → 红色 `Badge`「失败」+ `Tooltip` 显示错误原因
- 操作：删除、重建索引
- **轮询**：有文档处于中间态时，每 3s 拉一次列表；全部就绪后停止

**为什么轮询而不是 WebSocket**：后端没有推送通道，加 WS 是后端改动。3s 轮询在演示场景完全够用。

### 7.4 上传（`UploadDropzone`，嵌在详情页）

- 拖拽 + 点击选择，支持多文件
- 前端校验：扩展名（9 种）、大小上限（读后端配置）
- 上传中：每个文件一条进度（`XMLHttpRequest.upload.onprogress` 或 `fetch` + 无法取进度 → **选 XHR**）
- 上传完不等待索引，直接刷新列表并进入轮询

**取舍说明**：`fetch` 无法获取上传进度，演示场景下「进度条不动」观感很差，所以上传这一个点用 `XMLHttpRequest`。这是全项目唯一用 XHR 的地方。进度条用 `Progress` 组件。

### 7.5 问答（`ChatView`）

布局：左侧可折叠的引用/来源区，右侧对话流。

单轮消息结构：

```
用户气泡（问题）

助手气泡：
  [流式文本]
  ─────────────
  引用来源（CitationCard × N）
    [1] 文件名 · 第2页 · 相似度 0.83
  底部：耗时 8.2s · 模型 deepseek-chat
```

- 流式：`delta` 逐字追加，**光标动画**提示还在生成
- `meta` 事件到达时先渲染引用卡片骨架（`Skeleton`），用户能提前看到「找到了哪些资料」
- `done` 到达后：渲染 `caveat`（引用校验失败提示，用 `Alert` 的 warning 样式）
- `error` 事件：气泡内红色提示 + 「重试」按钮
- 拒答：正常显示（后端返回的是「资料中未提及…」，不是错误）

**多轮上下文**：前端维护 `history: [{role, content}]`，每次请求带上。切换知识库时清空。

## 八、视觉体系（shadcn-vue + Tailwind）

用户指定 UI 参考：**https://ui.shadcn.com/**

### 8.1 为什么不是原版 shadcn

shadcn/ui 是 **React 组件库**，不是 npm 依赖包——它把组件源码复制进项目。
Vue 生态的对应物是 `shadcn-vue`，组件 API 与视觉几乎一一对应：

| 原版（React） | 本项目（Vue） |
|---|---|
| `npx shadcn@latest add button` | `npx shadcn-vue@latest add button` |
| Radix UI | **reka-ui**（Radix 的 Vue 移植） |
| `className` | `class` |

**已核对版本**（2026-10-21，`npm view` 实际查询）：

```
shadcn-vue     2.8.2
tailwindcss    4.3.3
reka-ui        2.11.0
```

### 8.2 CSS 变量（HSL，shadcn 标准格式）

```css
/* src/styles/shadcn.css */
@layer base {
  :root {
    --background: 0 0% 100%;
    --foreground: 240 10% 3.9%;
    --card: 0 0% 100%;
    --card-foreground: 240 10% 3.9%;
    --popover: 0 0% 100%;
    --popover-foreground: 240 10% 3.9%;

    /* 主色：中性近黑（不用蓝色，见 8.3） */
    --primary: 240 5.9% 10%;
    --primary-foreground: 0 0% 98%;

    --secondary: 240 4.8% 95.9%;
    --secondary-foreground: 240 5.9% 10%;
    --muted: 240 4.8% 95.9%;
    --muted-foreground: 240 3.8% 46.1%;
    --accent: 240 4.8% 95.9%;
    --accent-foreground: 240 5.9% 10%;

    /* 语义色：只用于状态徽标与警示条 */
    --destructive: 0 72% 51%;
    --destructive-foreground: 0 0% 98%;

    --border: 240 5.9% 90%;
    --input: 240 5.9% 90%;
    --ring: 240 10% 3.9%;

    --radius: 0.5rem;
  }
}
```

`tailwind.config` 用 `hsl(var(--xxx))` 映射到 `bg-background` / `text-muted-foreground` 这类工具类。

### 8.3 为什么主色用中性黑而不是蓝

shadcn 的默认观感是「黑白灰 + 细边框 + 大留白」，蓝色主色会立刻偏离这个基调。

而且在这个 RAG 场景里，**引用卡片和状态徽标才是需要突出的信息**。主色如果也是蓝的，会和「引用」的视觉权重打架。

**状态色（只在这三处用）**：

| 语义 | 用色 | 出现位置 |
|---|---|---|
| 可用 / 成功 | `--destructive` 的互补绿（`152 60% 38%`） | 文档状态徽标 |
| 处理中 | 蓝（`217 91% 60%`） | 文档状态徽标、流式光标 |
| 失败 / 警示 | `--destructive` | 失败徽标、`caveat` 警示条 |

### 8.4 本轮要用到的 shadcn-vue 组件

提前列出来，F1 一次装齐，避免逐页 `add`：

```
button card input label table dialog tabs sonner
dropdown-menu separator badge skeleton scroll-area
tooltip alert progress avatar
```

**为什么不用 `form` 系列**：shadcn-vue 的 Form 依赖 `vee-validate` + `zod`，本项目只有登录一个表单，手写校验更轻。

**为什么用 `sonner` 而不是 `toast`**：sonner 是 shadcn 当前推荐的 toast 方案，原 `toast` 已标记弃用。

**本轮只做 A 的准备**（`npm run build` 能过 + 产物能被 FastAPI 挂载），不实际部署。

```json
"scripts": {
```

**规则**：`openapi.json` 与 `generated.d.ts` **都入库**。后端改接口后必须重跑，否则类型不同步——这条写进 README。
