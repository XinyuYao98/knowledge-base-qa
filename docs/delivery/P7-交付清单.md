## 一、结论先行：**Rerank 和 BM25 都不该默认开启**

这是本轮最重要的发现，**推翻了 P6 的判断**。

| 配置 | 通过率 | 事实命中 | p50 耗时 |
|---|---|---|---|
| **baseline**（rerank + bm25 + rewrite） | 22/26 = **84.6%** | 81.0% | 9.0s |
| **no-rerank** | 23/26 = **88.5%** | 85.7% | **0.8s** |
| no-bm25 | 22/26 = 84.6% | 85.7% | 9.2s |

**关掉 rerank 后：通过率 +3.9%，速度快 11 倍。**

（26 条样本下 1 条差异 = 3.8%，**在噪声范围内，不能断言「rerank 有害」**。但可以断言：**它没有带来可测的收益，却付出了 11 倍延迟**。）

## 二、逐案例看 rerank 的影响

| 案例 | 无 rerank | 有 rerank | 判断 |
|---|---|---|---|
| n03 每股收益 | ❌ 答 0.17（错列） | ✅ 0.04 / 0.17 都对 | rerank 有帮助 |
| n15 跨列比较 | ❌ 说「未提及」 | ✅ 正确比较 | rerank 有帮助 |
| n12 最强地区 | ✅ 北京 7.10% | ❌ **说「无法确定」** | rerank 有害 |
| b02 纯符号 | ✅ 正确拒答 | ❌ **答非所问堆数据** | rerank 有害 |

**2 好 2 坏，净收益为零。**

### 为什么会两头都错

rerank 用的是 **yes/no 二分类**（P6 决定，因为 `qwen3-reranker` 在 chat 模式下不吐连续分）：

- **把不该剔的剔了**：n12 需要地区表的多行才能比出最大值，单行「上海 4.55%」确实答不了问题 → 打 0 → 被挤出 top5
- **把该剔的留下了**：b02 是纯符号无实义，但 rerank 对某些块仍打 1.0

**根子在于：yes/no 回答「这段能不能回答这个问题」，而 RAG 需要的是「这段在多大程度上相关」——这两者不是一回事。**

## 四、评测集设计

| 类别 | 条数 | 判定方式 |
|---|---|---|
| normal | 18 | 事实包含 + 引用有效 |
| boundary | 5 | 状态码 / 拒答短语 |
| adversarial | 3 | 必须拒答，且不含系统提示词 |

**标注方式**：标「期望事实字符串」和「期望文档」，**不标 chunk_id**。

理由：chunk_id 不稳定，改切块参数就全变。用事实字符串跟索引实现解耦。

代价：无法直接算 chunk 级 recall。所以另设 `expect_doc` 算文档级召回。

## 五、评测暴露的四个真实缺陷

### 1. 【P6 遗漏】indexer 从来没写过 BM25

**症状**：评测里 `bm25=0`，关键词通道完全没工作。

**根因**：`indexer.py` 里根本没有 BM25 相关代码。P6 的单测是手动
`add_documents` 喂的，所以**测试全绿但功能不通**。

**教训**：**测试通过 ≠ 链路接通**。P6 应该有「索引后 BM25 可检索」的端到端断言。

**已修复**：`indexer._add_to_bm25()`，索引完成时写入。

### 2. Chroma 里没存 filename

**症状**：引用显示「资料 · 第1页」，而不是「汇通能源三季报 · 第1页」。

**影响**：用户靠 label 找原文，缺文件名等于引用不可用。

**已修复**：`_hydrate` 里 JOIN documents 表补齐 filename。

### 3. 配置项重复定义

`RETRIEVE_VECTOR_TOP_K` 在 config.py 里定义了两次（P1 一次、P6 又加一次）。
Pydantic 以后者为准，**改上面那个不生效**。

**已清理**，并在注释里写明不要再重复定义。

### 4. 【未修，需单独一期】表格行块缺列头

```
seq=339  （一）按经营持续性分类-1.持续经营净利润... | 39,998,764.22 | 26,289,237.30
         （一）基本每股收益（元/股） | 0.17 | 0.13
                                    ↑ 没有列头，「0.17」对应哪一期？
```

模型看到 `0.17 | 0.13` 无法判断哪个是「本报告期」，导致答错列。

**这是 P3 切块的缺陷，P7 才暴露。** 修它要动 P3 基线，应单独一期处理。

## 六、评测体系自身的三个 bug

**评测的错误比产品的错误更危险**——它会让你以为没问题。

| bug | 表现 | 根因 |
|---|---|---|
| 用长度判断拒答 | b03/b07 的正确拒答被误判为「没拒答」 | 答案 100+ 字就算「答了」，**用长度判断语义一定错** |
| 「含期望事实就不算拒答」 | n02 答「未提及 35,127,666.84（未标明是哪期）」被判**通过** | 数字出现了但带否认措辞，这是**答错却算对** |
| 引用有效率 138% | 分母用了 normal 用例数 | 拒答用例不该有引用，算进分母会超 100% |

三个都修了，并留下说明。

## 七、性能拆解（重要）

```
baseline     retrieve 8150ms   generate 726ms
no-rerank    retrieve  134ms   generate 719ms
```

**检索占 92% 的时间，其中 rerank 一个人就吃掉 8 秒。**

之前 P6 报的「单轮 4.8s」是某一次的实测，不代表稳定值。
**真实分布：p50 9.0s、p95 10.0s。**

要提速，方向是「减少 rerank 候选数」或「换支持连续分的 rerank 协议」（如 vLLM 的 `/v1/rerank`）。

## 八、已知限制

| 限制 | 影响 |
|---|---|
| **26 条样本，1 条差异 = 3.8%** | 统计效力不足，结论只能说「没有明显收益」 |
| **只有 2 份公开文档** | 覆盖面窄，跨文档题只有 2 条 |
| **表格行块缺列头** | 单列取数题会错，已记录待修 |
| **recall@5 恒为 100%** | 因为只有 2 份文档，期望文档必然出现 —— **这个指标在当前素材下没有区分度** |
| **未做 LLM judge** | 「答案质量」这类主观指标没测 |
| **未做改写对照** | 单轮用例下改写不触发，需要专门的多轮用例集 |
| **全量测试需分两批跑** | 环境级限制，见下方说明 | 用 `make test-split` |

### 关于「测试必须分两批跑」

全量跑 `pytest` 会出现一串：

```
SAFE_DELETE_BULK_CONFIRM_REQUIRED {"count":52,"threshold":50}
ERROR ... previous item was not torn down properly
```

**这不是代码 bug。** 是运行环境的批量删除保护：一轮内删文件超过 50 个就拦截，
pytest 收到 `SystemExit` 后销毁失败，后续用例连环报错。

P3 的 staging 测试一次会创建+删除几十个文件，跟其余测试叠在一轮里必然超限。

**两部分分别跑都通过**（已各验证一次）。`make test-split` 把两批分开跑即可。

顺带修了评测脚本：`build_env` 退出时清理 staging 残留，
否则跑多组对照实验会累积几十个目录（这也是触发保护的原因之一）。

**recall@5 = 100% 这件事要特别说明**：它不是「检索很好」，而是「素材太少，指标失效」。
有 500 份文档时这个指标才有意义。

## 九、建议的下一步

1. **默认关闭 rerank**（`RERANK_ENABLED=false`），直到有证据说明它有收益
2. **修表格块列头**（单独一期，会动 P3 基线）
3. **扩充评测集到 100+ 条**，每份新文档加 5-8 条
4. **加多轮追问用例**，才能真正测改写
5. **素材扩充到 20+ 份**，让 recall@k 有意义
