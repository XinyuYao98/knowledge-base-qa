## 一、结论先行

### 26 条时的结论是错的

第一轮用 26 条跑，得出「关掉 rerank 更好」。**这个结论不成立。**

26 条里 1 条差异 = 3.8%，而且后来又发现同一配置两次跑结果差 22%。
**样本量根本不足以支撑任何结论。**

### 109 条重跑后：rerank 确实有用

| 配置 | 通过率 | 事实命中 | p50 | p95 |
|---|---|---|---|---|
| **baseline（开 rerank）** | **93/109 = 85.3%** | 86.5% | 9.2s | 10.1s |
| no-rerank | 86/109 = 78.9% | 78.8% | **1.0s** | 1.6s |

**净 +7 条（+6.4%），代价是慢 9 倍。**

逐条看：rerank 救活 13 条（n02/n03/n15/n23/n25/n28/n31/n40/n49/n71/n81/n86/b11），
搞坏 6 条（n14/n37/n75/n77/n78/n80）。

### 但这 19 条全是表格取数题

两个方向的变化都指向**同一个根因**：表格行块丢了列头和项目名。

```
seq=26  的冲销部分 |  | 616,631.23 |       ← 项目名被截断
                                    ← 不知道是「本期」还是「年初至报告期末」
```

同一份数据在 `text` 块里是完整的（`非流动性资产处置损益…616,631.23`），
在 `table_row` 块里是残缺的。

**rerank 起的作用不是「排序更准」，而是「更倾向挑完整的 text 块，避开残缺的 table_row 块」。**

### 所以正确的处理是

1. **开 rerank**（它是当前唯一能缓解表格问题的手段）
2. **但它是创可贴** —— 修好表格切块后，这 13 条收益会消失，
   因为正确答案本来就在候选里，不需要靠 rerank 去躲坏数据

### 稳定性

| 项目 | 结果 |
|---|---|
| 3 轮 × 40 条一致率 | **92.5%** |
| 抖动用例 | 3 条（b02 / n21 / n26） |

**92.5% 一致率意味着：单次评测的结论有约 7% 的不确定性。**
所以「A 比 B 高 3%」这类结论都不该采信。

### 扩充方式：同一数据点用不同问法

不重复问同一句话，而是对同一份数据做不同角度的提问：

| 问法 | 例子 |
|---|---|
| 数值直取 | 营业收入是多少 |
| 跨列对比 | 本报告期 vs 年初至报告期末哪个高 |
| 同比变化 | 同比增长多少 |
| 条件筛选 | 哪些省份 R&D 经费超过 4000 亿 |
| 求最大/最小 | 投入强度最高的地区 |
| 负号/特殊值 | 非经常性损益合计（-50,738.50）、现金流量（不适用） |

### 期望值全部经过原文校验

第一版我凭记忆写了 72 条，核对时发现**两条错的**：

- 广东投入强度我写 3.6，实际 **3.78**
- 「超过 4000 亿的省份」我漏了广东（**5510.4 才是最高**）

所以加了 `scripts/expand_cases.py`：把每条 `expect_facts` 拿去原文精确匹配，
匹配不到就拒绝写入。最终 83 条通过校验、0 条可疑。

**凭记忆出题一定会错，必须用脚本校验。**

## 四、评测暴露的四个真实缺陷

### 1. 【P6 遗漏】indexer 从来没写过 BM25

**症状**：评测里 `bm25=0`，关键词通道完全没工作。

**根因**：`indexer.py` 里根本没有 BM25 相关代码。P6 的单测是手动
`add_documents` 喂的，所以**测试全绿但功能不通**。

**教训**：**测试通过 ≠ 链路接通**。P6 应该有「索引后 BM25 可检索」的端到端断言。

**已修复**：`indexer._add_to_bm25()`，索引完成时写入。

### 2. Chroma 里没存 filename

**症状**：引用显示「资料 · 第1页」，而不是「汇通能源三季报 · 第1页」。

**影响**：用户靠 label 找原文，缺文件名等于引用不可用。

**已修复**：`_hydrate` 里 JOIN documents 表补齐 filename。

### 3. 配置项重复定义

`RETRIEVE_VECTOR_TOP_K` 在 config.py 里定义了两次（P1 一次、P6 又加一次）。
Pydantic 以后者为准，**改上面那个不生效**。

**已清理**，并在注释里写明不要再重复定义。

### 4. 【未修，需单独一期】表格行块缺列头

```
seq=339  （一）按经营持续性分类-1.持续经营净利润... | 39,998,764.22 | 26,289,237.30
         （一）基本每股收益（元/股） | 0.17 | 0.13
                                    ↑ 没有列头，「0.17」对应哪一期？
```

模型看到 `0.17 | 0.13` 无法判断哪个是「本报告期」，导致答错列。

**这是 P3 切块的缺陷，P7 才暴露。** 修它要动 P3 基线，应单独一期处理。

## 五、评测体系自身的三个 bug

**评测的错误比产品的错误更危险**——它会让你以为没问题。

| bug | 表现 | 根因 |
|---|---|---|
| 用长度判断拒答 | b03/b07 的正确拒答被误判为「没拒答」 | 答案 100+ 字就算「答了」，**用长度判断语义一定错** |
| 「含期望事实就不算拒答」 | n02 答「未提及 35,127,666.84（未标明是哪期）」被判**通过** | 数字出现了但带否认措辞，这是**答错却算对** |
| 引用有效率 138% | 分母用了 normal 用例数 | 拒答用例不该有引用，算进分母会超 100% |

三个都修了，并留下说明。

## 六、性能拆解（重要）

109 条实测：

| 配置 | p50 | p95 |
|---|---|---|
| 开 rerank | 9.2s | 10.1s |
| 关 rerank | **1.0s** | 1.6s |

**检索占 92% 的时间，rerank 一个人吃 8 秒。**

P6 报的「单轮 4.8s」是某一次的实测，不代表稳定值。
**真实分布：开 rerank p50 9.2s。**

要提速，方向是「减少 rerank 候选数」或「换支持连续分的 rerank 协议」（如 vLLM 的 `/v1/rerank`）。

## 七、已知限制

| 限制 | 影响 |
|---|---|
| **只有 2 份文档** | recall@k 恒为 100%，该指标在当前素材下无区分度 |
| **单次评测约 7% 不确定** | 92.5% 一致率，3% 以内的差异不该采信 |
| **表格切块缺陷未修** | 表格题批量抖动，是当前最大的质量问题 |
| **表格行块缺列头** | 单列取数题会错，已记录待修 |
| **recall@5 恒为 100%** | 因为只有 2 份文档，期望文档必然出现 —— **这个指标在当前素材下没有区分度** |
| **未做 LLM judge** | 「答案质量」这类主观指标没测 |
| **未做改写对照** | 单轮用例下改写不触发，需要专门的多轮用例集 |
| **全量测试需分两批跑** | 环境级限制，见下方说明 | 用 `make test-split` |

### 关于「测试必须分两批跑」

全量跑 `pytest` 会出现一串：

```
SAFE_DELETE_BULK_CONFIRM_REQUIRED {"count":52,"threshold":50}
ERROR ... previous item was not torn down properly
```

**这不是代码 bug。** 是运行环境的批量删除保护：一轮内删文件超过 50 个就拦截，
pytest 收到 `SystemExit` 后销毁失败，后续用例连环报错。

P3 的 staging 测试一次会创建+删除几十个文件，跟其余测试叠在一轮里必然超限。

**两部分分别跑都通过**（已各验证一次）。`make test-split` 把两批分开跑即可。

顺带修了评测脚本：`build_env` 退出时清理 staging 残留，
否则跑多组对照实验会累积几十个目录（这也是触发保护的原因之一）。

**recall@5 = 100% 这件事要特别说明**：它不是「检索很好」，而是「素材太少，指标失效」。
有 500 份文档时这个指标才有意义。

## 八、建议的下一步

按优先级：

| 优先级 | 事项 | 理由 |
|---|---|---|
| **P0** | **修表格切块：项目名不截断 + 带列头** | 当前最大质量问题，直接影响 19 条用例 |
| **P0** | 保持 rerank 开启 | 109 条实测净 +7 条 |
| P1 | 素材扩到 20+ 份文档 | 让 recall@k 有意义（现在恒为 100%） |
| P1 | 评测集扩到 200+ 条 | 进一步压低不确定性 |
| P2 | 加多轮追问用例 | 才能真正测改写 |
| P2 | 温度降到 0 | 事实问答应确定性输出 |

### 关于表格切块

这是 P3 的欠账，修它要动 P3 的解析基线。但**不修的话，所有表格类问题都会持续抖动**。

具体缺陷（实测）：
1. 项目名被跨行切断 → `的冲销部分`（丢了前半截）
2. 行块不带列头 → `616,631.23` 不知道对应哪一期
3. 同一份数据在 text 块里完整、在 table_row 块里残缺，导致检索到哪个就答成什么样
