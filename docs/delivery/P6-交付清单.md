## 四、修掉的三个真实缺陷

### 1. Chroma 的 id 与 PG 的 chunk_id 不一致（架构级）

```
Chroma:  {doc_id}_{seq}
PG:      UUID
```

检索融合后按 UUID 回查原文 → **查不到** → BM25 命中的块全被丢弃。

**这是 P6 最严重的问题**：它不会报错，只表现为「BM25 好像没起作用」。

**修法**：
1. `Chunk` 加 `chunk_id` 字段
2. `chroma_store.add_chunks` 优先用它当 id
3. `indexer` 插入 PG 后按 `seq` 回查真实 UUID 回填

已有 2 个测试守住这个契约。

### 2. 只被 BM25 命中的候选被丢弃

第一版 `_hydrate` 跳过了它们。**那等于让 BM25 失效**，因为它存在的意义就是召回向量找不到的关键词匹配（`P-001`、`OCR`）。

改为回 PG 补全文本与元数据（需要传 `user_id` 设 RLS 上下文）。

### 3. 极小语料下 IDF 为负，检索永远为空

`BM25Okapi` 在 N=1 时所有词 IDF ≈ -0.27，得分全负，被 `score <= 0` 过滤。

库内置的 epsilon 截断在「平均 IDF 也是负」时同样失效。

**修法**：语料 < 3 篇时改用「查询词覆盖率」打分。

## 五、两个被实测推翻的预判

### 「新增文档要重建全量索引」——错的

`rank_bm25.add_document` 是增量的。真正触发重建的是**删除 / 修改**（corpus 是 list，删中间元素会让后续下标全部错位）。

### 「重建代价 403 块 30-50ms」——高估 10 倍以上

实测：**403 块 2.5ms、2000 块 12ms**。

墓碑机制保留的理由因此从「避免大开销」变成「避免查询路径上的 CPU 抖动」。

## 六、⚠️ 未验证：Rerank 的真实效果

**当前 LM Studio 没有加载 `qwen3-reranker-0.6b`。**

实测日志：
```
rerank_fallback_to_chat  reason=RuntimeError
```

所以本轮 rerank 走的都是**降级路径**（保留 RRF 顺序）。

**这意味着「rerank 是否真的提升排序质量」完全没有验证。**

要验证需要：
1. LM Studio 加载 `qwen3-reranker-0.6b`（或任意可打分的模型）
2. 跑 `pytest -m "db and real_model"` 看 `protocol` 是否为 `endpoint` / `chat`（而非 `fallback`）
3. 构造对照：同一问题，比较 rerank 前后的顺序差异是否合理

**这条不补，P6 只能说「流程通了」，不能说「检索质量达标」。**

| **单库全部文档常驻内存** | 大库内存压力 | 懒加载 + 按库分文件 |
| **固定窗口限流** | 边界处 2 倍通过 | P5 遗留，demo 可接受 |

### 改编写的一个观察

实测改写结果：
```
原问题：那它的上限呢？
改写后：根据资料，一线城市住宿标准的上限是每晚不超过 480 元吗？
```

**改写器把「答案」也写进去了。** 这不完全是坏事（检索更容易命中），
但它**改变了问题性质**：从「询问上限」变成「确认上限」。

提示词里有「不引入对话中没有的信息」，模型违反了这条。
后续可考虑：在提示词里加一个反例，或对改写结果做长度约束（比如不超过原问题 3 倍）。
