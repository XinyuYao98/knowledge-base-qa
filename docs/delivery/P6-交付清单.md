## 四、修掉的三个真实缺陷

### 1. Chroma 的 id 与 PG 的 chunk_id 不一致（架构级）

```
Chroma:  {doc_id}_{seq}
PG:      UUID
```

检索融合后按 UUID 回查原文 → **查不到** → BM25 命中的块全被丢弃。

**这是 P6 最严重的问题**：它不会报错，只表现为「BM25 好像没起作用」。

**修法**：
1. `Chunk` 加 `chunk_id` 字段
2. `chroma_store.add_chunks` 优先用它当 id
3. `indexer` 插入 PG 后按 `seq` 回查真实 UUID 回填

已有 2 个测试守住这个契约。

### 2. 只被 BM25 命中的候选被丢弃

第一版 `_hydrate` 跳过了它们。**那等于让 BM25 失效**，因为它存在的意义就是召回向量找不到的关键词匹配（`P-001`、`OCR`）。

改为回 PG 补全文本与元数据（需要传 `user_id` 设 RLS 上下文）。

### 3. 极小语料下 IDF 为负，检索永远为空

`BM25Okapi` 在 N=1 时所有词 IDF ≈ -0.27，得分全负，被 `score <= 0` 过滤。

库内置的 epsilon 截断在「平均 IDF 也是负」时同样失效。

**修法**：语料 < 3 篇时改用「查询词覆盖率」打分。

## 五、两个被实测推翻的预判

### 「新增文档要重建全量索引」——错的

`rank_bm25.add_document` 是增量的。真正触发重建的是**删除 / 修改**（corpus 是 list，删中间元素会让后续下标全部错位）。

### 「重建代价 403 块 30-50ms」——高估 10 倍以上

实测：**403 块 2.5ms、2000 块 12ms**。

墓碑机制保留的理由因此从「避免大开销」变成「避免查询路径上的 CPU 抖动」。

## 六、Rerank 真实验证（已通过）

加载 `qwen3-reranker-0.6b` 后重跑，**协议从 fallback 变成 chat**。

### 效果对比

问题：「一线城市出差住宿标准是多少？」

| 资料 | RRF 排名 | Rerank 后 | 分数 |
|---|---|---|---|
| 一线城市住宿标准每晚不超过480元 | #2 | **#1** ✅ | 1.00 |
| 供应商每年复审一次 | #3 | #2 | 0.50 |
| 员工出差期间市内交通费 | **#1** | #3 ✅ | 0.00 |
| 合同用印需法务审核 | #4 | #4 | 0.00 |
| 二线城市住宿标准 | #5 | #5 | 0.00 |

**这正是 rerank 的价值**：RRF 因为「出差」词面重叠把交通费排在第一，
rerank 判定它答不了「住宿标准」，把它压到第三，把正确答案提到第一。

耗时约 2.0s（5 条候选，并发 4）。

### 踩到的三个实现问题

**1. LM Studio 对 `/v1/rerank` 返回 200 + error 体**

```
HTTP 200
{"error":"Unexpected endpoint or method. (POST /v1/rerank)"}
```

只判 `status_code == 404` 会漏掉。虽然靠「results 为空」也能回退，
但那是副作用，不是显式判断。已改为识别 `error` 字段。

**2. 要求「输出 0-1 小数」时负例全解析失败**

模型的负例输出形如：
```
"无关\n\n没有关联\n\n请提供更多信息。\n</think>\n\n无关联"
```

**里面根本没有数字** → 全被解析成中性 0.5 → **rerank 等于没做**。

改为 **yes/no 二分类**：正例 `"yes"` 干净，负例虽带推理但必有 `no`。

**3. 模型偶尔「推理到死」**

某些资料上会持续推理直到 token 耗尽：`content=""`、`finish_reason=length`、
`reasoning_tokens≈254`。加大 max_tokens 治不了 —— 它不是在写结论，是在绕圈。

试过「换短提示词重试」，**更糟**：简化提示词下模型更容易说 yes，
实测把「交通费」（应判 0）误判成 1.00。**假阳性比中性分危害大得多**。

最终选择：判不出来就给 0.5（排序时夹在中间），不冒险翻成 yes。

## 七、已知问题

| 问题 | 影响 | 处理 |
|---|---|---|
| **Rerank 判定较粗** | 只有 yes/0.5/no 三档，非连续分数 | 部分资料会「推理到死」给中性分；改用 `/v1/rerank` 协议的服务可得连续分 |
| **改写会带入答案** | 「那它的上限呢」→「…上限是480元吗」 | 见下方说明，改变问题性质 |
| **流式无法修复引用** | 用户已看到内容，只能标注 | 已加 `caveat` 字段 |
| **query_logs 不存原文答案** | P7 评测缺原料 | 表结构如此，P7 需单独建评测表 |
| **BM25 快照需手动 flush** | 进程崩溃会丢最新写入 | 可从 PG 全量重建 |
| **单库全部文档常驻内存** | 大库内存压力 | 懒加载 + 按库分文件 |
| **生成依赖云端 API** | 离线不可用、有网络延迟 | 实测 4.8s；如需离线可换 instruct 小模型 |
| **无空答案以外的模型异常分类** | 只统一报 ModelServiceError | P7 可细化 |
| **固定窗口限流** | 边界处 2 倍通过 | P5 遗留，demo 可接受 |

### 改编写的一个观察

实测改写结果：
```
原问题：那它的上限呢？
改写后：根据资料，一线城市住宿标准的上限是每晚不超过 480 元吗？
```

**改写器把「答案」也写进去了。** 这不完全是坏事（检索更容易命中），
但它**改变了问题性质**：从「询问上限」变成「确认上限」。

提示词里有「不引入对话中没有的信息」，模型违反了这条。
后续可考虑：在提示词里加一个反例，或对改写结果做长度约束（比如不超过原问题 3 倍）。
