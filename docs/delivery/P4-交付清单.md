## 三、状态机

```
                 ┌──────────────────────────────┐
                 ▼                              │
pending → parsing → chunking → embedding → ready ┘
   │         │          │           │
   └─────────┴──────────┴───────────┴──→ failed → pending
                                       │
                                       └──→ waiting_model
```

**三条允许的「回退」路径，都是实测加上的**：

| 路径 | 场景 | 不加会怎样 |
|---|---|---|
| `ready → pending` | 用户点「重新索引」 | 直接 `TransitionError`，重跑被拒 |
| `parsing/chunking/embedding → pending` | 用户改参数想重来 | 必须走完全程才能重置 |
| `failed → parsing` | 修好源文件后直接重试 | 得多绕一步 |

第一版把 `ready` 当纯终态，重跑测试直接失败——**这是集成测试抓出来的，不是想出来的**。

## 四、一个重要的架构决策：worker 用管理员连接

### 问题

`ingest_jobs` 和 `documents` 都受 RLS 保护，策略是 `user_id = current_setting('app.user_id')`。

但 worker 的职责恰恰是**跨用户调度**：

```
领任务（此时不知道是哪个用户的）
  → 才知道 user_id
  → 才能设置 RLS 上下文
```

鸡生蛋。

### 三个方案与选择

| 方案 | 后果 | 结论 |
|---|---|---|
| 给应用角色 BYPASSRLS | **API 也能绕过隔离** —— 整个 P1 的隔离失效 | ❌ |
| 给 ingest_jobs 加「读全部」策略 | 领任务解决了，但写 documents 仍被拦 | ❌ 治标 |
| **worker 用管理员连接，API 仍用应用角色** | 隔离边界不变，提权仅限受信任组件 | ✅ |

### 安全边界

- 管理员连接**只在 worker 进程内**，不进 API、不进请求上下文
- worker 写业务表前**仍显式 `set_config('app.user_id')`** —— 不是无脑绕过
- 生产环境应给 worker 单独账号（`kbworker`，BYPASSRLS），不复用 postgres 超级用户

## 五、实测踩到的四个问题

### 1. pytest-asyncio 用 ProactorEventLoop（第三次遇到）

P1 试过 `set_event_loop_policy`，**在 Python 3.13 上完全无效**。

这次找到正解：pytest-asyncio 有内部 fixture `_asyncio_loop_factory`，
在 `tests/p4/conftest.py` 覆盖它即可，不需要碰全局策略。

**放在子目录而不是全局 conftest**：其他测试都是同步的，不该被影响。

### 2. RLS 拦住了测试准备数据

```
InsufficientPrivilege: new row violates row-level security policy for table "users"
```

这不是 bug，是 P1 的隔离在正常工作。测试改用管理员连接准备用户/知识库，
异步会话只测业务逻辑。

### 3. worker 领不到任务

`claim_one()` 用普通会话执行，没设 RLS 上下文 → 查不到任何任务 →
worker 启动后立刻退出（日志只有 `worker_start` 和 `worker_exit`）。

**修复**：worker 改用管理员连接，见 §四。

### 4. 重跑索引被状态机拒绝

`ready` 被当成纯终态，重新索引时 `update_status(parsing)` 直接抛 `TransitionError`。

**修复**：允许 `ready → parsing`，并在 indexer 里「先打回 pending 再走正常流程」。

## 六、真模型端到端验收（已通过）

**模型**：`text-embedding-qwen3-embedding-4b`（2560 维）· **测试**：`pytest -m "db and real_model"`

| 用例 | 结果 |
|---|---|
| 真实 PDF → ready | ✅ 403 块，18.0s |
| 真实 HTML → ready | ✅ 200 块，7.5s |
| 向量维度 == 配置 | ✅ 2560 |
| 真实重索引 | ✅ 块数稳定，不重复 |
| worker 真实消费队列 | ✅ 403 块到 ready |

### 实测性能

**PDF（12 页、13 张表、403 块）**

| 阶段 | 耗时 | 说明 |
|---|---|---|
| parse | 1805ms | 12 页文本 + pdfplumber 表格 |
| chunk | 0.7ms | 32 解析块 → 403 切块 |
| **embed** | **15511ms** | **26 块/秒** |
| Chroma 写入 | ~180ms | |
| 合计 | **18.0s** | |

**HTML（6 张表、200 块）**：解析 198ms、向量化 6913ms、合计 7.5s。

### 重跑的表现（最能说明 P3 指纹的价值）

```
第一次：index_done  ms=17999.5
第二次：stage_reused  parse / chunk / embed   ← 三层全复用
        chunks_replaced  deleted=403
        chroma_add  count=403
        index_done  ms=524.7
```

**18 秒 → 0.5 秒，36 倍。** 且 `deleted=403` 证明旧块被替换而非重复堆积。

### 向量化速度值得注意

26 块/秒。一个 400 块的文档要 15 秒。如果将来支持批量上传，
这个速度会成为瓶颈 —— 当前 `EMBED_CONCURRENCY=2` 可以再调，
但要先确认 LM Studio 能否吃住更高并发。

## 七、已知问题

| 问题 | 影响 | 处理 |
|---|---|---|
| **BM25 未实现** | 检索只有向量通道 | 按决定挪到 P6 |
| **秒传只做同库** | 跨库同文件会重复索引 | 可接受（用户隔离） |
| **Chroma 失败不回滚 PG** | 可能出现「PG 有块、Chroma 无向量」 | 重跑可修复；`make reindex` 兜底（P6） |
| **单文档超时 600s** | 超大文件可能超时 | 重试 3 次后失败，用户可重传 |
| **worker 无优雅停机** | Ctrl+C 时可能在处理中途退出 | 已加载任务会跑完；未做的留着下次 |
| **未接 API** | 只能 CLI 上传 | P5 补 |
| **⚠️ 用户注册路径缺失** | `users` 表受 RLS 保护，策略只允许 `id = current_setting('app.user_id')`，**应用角色连注册用户都插不进去** | **P5 必须解决**：用 SECURITY DEFINER 函数（`auth_register`）或管理员连接，不能让 API 直接 INSERT |
| **upload CLI 需管理员连接** | 建测试用户走了 `DATABASE_ADMIN_URL` | P5 做 API 时走 SECURITY DEFINER，不再需要 |
