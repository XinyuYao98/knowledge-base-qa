## 三、状态机

```
                 ┌──────────────────────────────┐
                 ▼                              │
pending → parsing → chunking → embedding → ready ┘
   │         │          │           │
   └─────────┴──────────┴───────────┴──→ failed → pending
                                       │
                                       └──→ waiting_model
```

**三条允许的「回退」路径，都是实测加上的**：

| 路径 | 场景 | 不加会怎样 |
|---|---|---|
| `ready → pending` | 用户点「重新索引」 | 直接 `TransitionError`，重跑被拒 |
| `parsing/chunking/embedding → pending` | 用户改参数想重来 | 必须走完全程才能重置 |
| `failed → parsing` | 修好源文件后直接重试 | 得多绕一步 |

第一版把 `ready` 当纯终态，重跑测试直接失败——**这是集成测试抓出来的，不是想出来的**。

## 四、一个重要的架构决策：worker 用管理员连接

### 问题

`ingest_jobs` 和 `documents` 都受 RLS 保护，策略是 `user_id = current_setting('app.user_id')`。

但 worker 的职责恰恰是**跨用户调度**：

```
领任务（此时不知道是哪个用户的）
  → 才知道 user_id
  → 才能设置 RLS 上下文
```

鸡生蛋。

### 三个方案与选择

| 方案 | 后果 | 结论 |
|---|---|---|
| 给应用角色 BYPASSRLS | **API 也能绕过隔离** —— 整个 P1 的隔离失效 | ❌ |
| 给 ingest_jobs 加「读全部」策略 | 领任务解决了，但写 documents 仍被拦 | ❌ 治标 |
| **worker 用管理员连接，API 仍用应用角色** | 隔离边界不变，提权仅限受信任组件 | ✅ |

### 安全边界

- 管理员连接**只在 worker 进程内**，不进 API、不进请求上下文
- worker 写业务表前**仍显式 `set_config('app.user_id')`** —— 不是无脑绕过
- 生产环境应给 worker 单独账号（`kbworker`，BYPASSRLS），不复用 postgres 超级用户

## 五、实测踩到的四个问题

### 1. pytest-asyncio 用 ProactorEventLoop（第三次遇到）

P1 试过 `set_event_loop_policy`，**在 Python 3.13 上完全无效**。

这次找到正解：pytest-asyncio 有内部 fixture `_asyncio_loop_factory`，
在 `tests/p4/conftest.py` 覆盖它即可，不需要碰全局策略。

**放在子目录而不是全局 conftest**：其他测试都是同步的，不该被影响。

### 2. RLS 拦住了测试准备数据

```
InsufficientPrivilege: new row violates row-level security policy for table "users"
```

这不是 bug，是 P1 的隔离在正常工作。测试改用管理员连接准备用户/知识库，
异步会话只测业务逻辑。

### 3. worker 领不到任务

`claim_one()` 用普通会话执行，没设 RLS 上下文 → 查不到任何任务 →
worker 启动后立刻退出（日志只有 `worker_start` 和 `worker_exit`）。

**修复**：worker 改用管理员连接，见 §四。

### 4. 重跑索引被状态机拒绝

`ready` 被当成纯终态，重新索引时 `update_status(parsing)` 直接抛 `TransitionError`。

**修复**：允许 `ready → parsing`，并在 indexer 里「先打回 pending 再走正常流程」。
