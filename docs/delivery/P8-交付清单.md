## 二、更重要的：一个被推翻的方案

### P8 中间版本把表格按行切碎了，指标反而下降

| 版本 | 通过率 |
|---|---|
| P7 修复前 | 86/109 = 78.9% |
| P8 第一版（行级切块） | 83/109 = 76.1% |
| P8 第二版（修完子表/表头） | 81/109 = **74.3%** |

**修了越多缺陷，指标越低。** 这不是 bug 越修越糟，而是**行级切块本身错了**。

### 证据：答案在库里，却挤不进候选

n07 问「第一大股东是谁，持股比例多少」，行级切块下的候选是：

```
[1] 页眉：上海汇通能源…证券代码：600605
[2] 封面页眉
[3] 注：本报告期指本季度初至…
[4] 厦门驱动力 5.53%（第 3 大股东）
[5] 香港中央结算 1.19%（第 6 大股东）
    ← 西藏德锦 26.81%（第一大股东）不在候选里
```

**根因**：单行块之间高度相似（46 行行业表每行都是「XX: 数字 / YY: 数字」），
向量 top20 几乎等于随机抽样；而页眉因含公司名，反而排最前。

**切碎解决不了排序问题，只会把「一整张表」的信息密度打散。**

### 定稿方案：一张表一个块

```
列：股东名称 / 股东性质 / 持股数量 / 持股比例(%) / … 
西藏德锦企业管理有限责任公司 | 境内非国有法人 | 55,307,275 | 26.81 | 0 | 质押 | 37,963,500
厦门驱动力私募基金管理有限公司－驱动力光华1号私募证券投资基金 | 其他 | 11,400,000 | 5.53 | 0 | 无 | 0
…
```

- 块数：311 → **39**
- 10 位股东在同一个块里，模型能判断「谁是第一」
- 超长表（>800 字符）才切分，且每块重复列名声明

## 三、修了什么（按文件）

### `app/rag/chunker.py`

| 改动 | 原因 |
|---|---|
| `_chunk_table` 改用 `cells` 重建 | 文本按 `\n` 分行会切断跨行项目名 |
| 一张表一个块（不再逐行） | 见 §二 |
| `_merge_header` 多行表头逐列合并 | PDF 表头常跨 2-3 行 |
| `_format_row` 输出 `a \| b \| c` + 顶部 `列：` 声明 | 消除「数竖线数错列」 |
| `_looks_like_subtable_header` | 一个 block 装两张表时切换列名 |
| 空值写「（空）」 | 区分「这格是空的」与「没这行」 |
| 无表头时写「（本表无表头）」 | 避免模型编造字段名 |

### `app/rag/parsers/pdf.py`

| 改动 | 原因 |
|---|---|
| 按表格 bbox 切条带，从正文排除表格区域 | 消除「同一张表出现两次」 |
| `_looks_like_header_row` | 首行含数字 ≠ 无表头（股东表 r1 有 13,587） |
| `_looks_like_data_row` | 利润表续页首行是数据，不是表头 |
| 表头行号占位 | `header_rows=2` 但只写了 row=0 时，下游会取到 [0, 2] |
| 去整列全空的首列 | 跨页表常有空首列，导致每行标题都是空 |

### `scripts/parse_report.py`

字符数下降不再一律判回归 —— **含表格的文件**下降可能是去重（P8 从 20706→12055 是修复不是回归）。

## 四、踩到并修正的实现错误（共 5 个）

这一轮我在实现上错了 5 次，全部靠实测揪出来：

1. **`_looks_like_data_row` 判据过激进**
   首行含数字就判「无表头」→ 股东表 r1（`报告期末普通股股东总数 | 13,587`）被当数据，
   r3 的真列名降级，整表不可用。
   → 改为往后看 4 行，找「最像列名」的那行。

2. **`cells` 行号被压平**
   表头写 row=0、数据从 row=1 起 → 下游无法区分「表头占几行」。
   → 保留真实行号。

3. **表头行号有空洞**
   `header_rows=2` 但只写了 row=0，下游取 `row_ids[:2]` 得到 [0, 2]，
   **把第一条数据当成表头** → 列名变成「股东名称 西藏德锦企业管理有限责任公司」。
   → 表头每行都写占位。

4. **子表头判据太宽松**
   「无数字 + 短 + 多列」→ `西藏德锦 | 人民币普通股`（纯文本数据行）也被判成表头，
   第一条股东数据被吃掉。
   → 改成「必须与当前列名有重复」。

5. **长度检查挡住了后面的分支**
   `all(len(v) <= 14)` 放在最前面 `return False`，
   导致「首列为空」的新分支永远走不到。
   → 把长度检查移到分支内部。

**共性**：5 个都是「判据写得太宽或太窄」，而且**没有一个被单元测试发现**，
全部是拿真实 PDF 跑出来才暴露的。

## 六、⚠️ 已知问题（未修，需单独一期）

以下问题**与表格切块无关**，但被本轮评测暴露，是当前最大的两块短板：

### 1. 页眉污染检索（影响面最大）

PDF 每页页眉都是「上海汇通能源股份有限公司 2026年第三季度报告 …」，
且被解析器**合并进了正文段首**。

后果：任何含「汇通能源」的问题，页眉的向量相似度都极高，稳居候选前列；
真正的数据块被挤出 top5。

n41（第二大股东）的 5 条候选**全是页眉和无关注释**，股东表一条都没进。

### 2. reranker 在 chat yes/no 模式下不具精排能力

实测（同一批候选，串行 2 次 vs 并发 2 次）：

| 跑法 | 全国总量 | 附表标题 | **江苏 4948.2（正确）** | 附表标题 | 北京 |
|---|---|---|---|---|---|
| 串行 ×2 | 1.0 | 1.0 | **1.0** | 1.0 | 0.0 |
| 并发 ×2 | 1.0 | 1.0 | **1.0 / 0.0** | 0.0 / 0.5 | 0.0 |

- 它几乎对什么都回答 yes，正确答案无唯一高分
- 并发下同一输入两次结果不同（`c3` 一次 1.0 一次 0.0）

**P7 结论「rerank 贡献 +6.4%」因此需要重新审视** —— 那次收益可能只是
「长块里所有数据混在一起，碰巧被选中」。

当前 `.env` 中 `RERANK_ENABLED=false`，待决策。

### 3. `recall@k` 无区分度

只有 2 份文档，期望文档必然出现在候选里，**recall@5 恒为 100%**。
要让它有意义，素材需扩到 20+ 份。
